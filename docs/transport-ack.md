# Transport ACK Protocol

Created: 2026-06-23

This document specifies the application-level framing and acknowledgement
protocol implemented in `src/transport.rs`. The protocol was added in
`bbc098d` / `280a032` and its semantics were pinned down by the 26 host tests
landed in `55faba2` (`src/transport.rs` tests module). It runs on top of the
Enhanced ShockBurst (ESB) radio core to give split-keyboard firmware an
end-to-end reliable channel.

The radio core (`src/isr.rs`, `src/state_machine.rs`) transmits arbitrary
payload bytes and does not interpret this format. Applications may use these
helpers in a board-level transport adapter for routing, duplicate suppression,
and application acknowledgements.

## Overview

ESB by itself is a one-hop radio protocol: one PTX transmits, one PRX replies
with a hardware ACK, and the PTX retransmits up to `retransmit.count` times if
no ACK arrives. That is enough for a single packet inside a single radio
session, but a split keyboard needs more:

- Frames must outlive a single radio session. Under MPSL timesharing, the radio
  is periodically taken away from ESB for BLE (`docs/m10-verification.md`),
  which means a frame queued at time T may not be delivered until a later ESB
  timeslot.
- The central (left half) may reboot or re-pair. After a restart the PRX side
  has no memory that a given frame was already delivered, so the peripheral
  (right half) must be able to retransmit safely without duplicating state on
  the central.
- Frames from different devices arrive on different pipes, so the central needs
  a cheap way to validate `pipe -> device` routing before acting on a frame.

The transport layer in `src/transport.rs` provides three things on top of the
raw ESB payload path:

1. A small fixed `TransportHeader` carrying version, device id, sequence
   number, flags, and payload length.
2. A 4-byte application ACK carried back inside an ESB ACK payload, identifying
   the exact `(device_id, sequence)` being acknowledged.
3. Helpers for `pipe -> device_id` binding (`StaticBindingTable`) and per-device
   duplicate suppression (`SequenceTracker`), combined in
   `accept_bound_frame`.

## Two Layers of Acknowledgement

This is the key design choice and deserves its own section.

### Layer 1: ESB hardware ACK (radio link)

Implemented in `src/state_machine.rs` and driven from `src/isr.rs`. After every
PTX transmission that does not set the ESB `NO_ACK` bit, the PTX state machine
enters `WaitAck` and the PRX state machine enters `TxAck`. The PRX replies on
the same pipe with a hardware ACK packet that may carry an ACK payload
(`StatePrx::TxAck` / `TxRepeatedAck` in `src/state_machine.rs`).

Properties of the ESB hardware ACK:

- **Single hop, single pipe.** It confirms that one PRX heard one packet on one
  pipe. It does not know which application frame the packet carried.
- **Single session.** It is generated by the radio state machine while the radio
  is owned by ESB. When ESB is suspended (for BLE, or for any MPSL timeslot
  handback), in-flight ACK state is dropped. `PtxStateMachine::do_suspend`
  releases the current TX and ACK buffers and returns to `Idle`
  (`src/state_machine.rs`).
- **Bounded retries.** The PTX retransmits at most `retransmit.count` times
  before signalling `PtxEvent::MaxAttempts` and dropping the packet
  (`src/state_machine.rs`, `WaitAck` branch). If the radio is taken away before
  those retries run out, the packet is simply lost from the radio's point of
  view.
- **Duplicate detection only at the radio level.** ESB uses a 2-bit PID plus CRC
  to suppress radio-level retransmits of the same packet on the same pipe
  (`PrxStateMachine::check_duplicate` in `src/state_machine.rs`). The PID wraps
  every four packets, so it cannot be used as an application-level sequence.

In short: the ESB hardware ACK answers *"did the radio link deliver this one
packet during this session?"* It does not answer *"did the application on the
other side process this frame?"*

### Layer 2: Transport ACK (application, end-to-end)

Implemented in `src/transport.rs` and carried back as an ESB ACK payload. When
the PRX application accepts a frame, it produces a `TransportAck` whose payload
is `TRANSPORT_ACK_MAGIC` plus the `device_id` and `sequence` of the accepted
frame. The PTX application matches that against the frame it just sent and only
then considers the frame delivered.

Properties of the transport ACK:

- **End-to-end.** It is produced by the receiving application (after binding and
  duplicate checks), not by the radio. It survives radio session boundaries
  because it is matched in the PTX application task, not in the radio ISR.
- **Keyed by `(device_id, sequence)`.** It identifies a specific application
  frame, not a radio packet.
- **Deduplicated by `SequenceTracker`.** The PRX side keeps the last accepted
  sequence per device and drops repeats at the application level, independent of
  radio PID.

### Why both layers are needed

The ESB hardware ACK only proves the PRX radio received a packet in the current
session; it says nothing about whether the application actually processed the
frame, and its guarantee vanishes at every timeslot boundary, every central
restart, and every max-attempt drop. The transport ACK closes that gap by
identifying the accepted frame at the application level and letting the PTX
retransmit across timeslots and reboots until that specific `(device_id,
sequence)` is acknowledged.

The ESB hardware ACK is still load-bearing: it is the fast, cheap, single-pipe
backchannel that the transport ACK piggybacks on. The split is "hardware ACK
for one-hop, in-session delivery; transport ACK for end-to-end, cross-session
delivery with dedup."

## Frame Format

`TransportHeader` is a 5-byte prefix in front of an application payload
(`src/transport.rs`):

```text
byte 0: protocol version   (must equal TRANSPORT_VERSION = 1)
byte 1: device id
byte 2: sequence number
byte 3: flags
byte 4: payload length
byte 5..: serialized higher-level payload
```

Constants (`src/transport.rs`):

| Constant | Value | Meaning |
|----------|-------|---------|
| `TRANSPORT_VERSION` | `1` | Current framing version. Decoding rejects any other value. |
| `TRANSPORT_HEADER_LEN` | `5` | Header size in bytes. |
| `MAX_TRANSPORT_PAYLOAD_LEN` | `247` | Largest higher-level payload that fits in one frame, i.e. `EsbHeader::MAX_PAYLOAD (252) - TRANSPORT_HEADER_LEN (5)`. |
| `FLAG_ACK` | `0x01` | Frame carries an application-level acknowledgement. |
| `FLAG_RETRANSMIT` | `0x02` | Frame is an application-level retransmit of an earlier sequence. |
| `FLAGS_V1_MASK` | `0x03` | All flags defined by transport v1 (`FLAG_ACK \| FLAG_RETRANSMIT`). |

Both encoding paths (`TransportHeader::new`, `TransportHeader::decode`) reject
any flag bit outside `FLAGS_V1_MASK`, so bits `0x04..0x80` are reserved. The two
defined flags are disjoint and may be set together (covered by
`v1_flags_are_disjoint_and_combine_into_mask` and
`transport_header_accepts_both_flags_set_together`).

The whole frame is placed in the ESB payload as-is; the ESB core does not
interpret it. Sizing helpers:

- `required_esb_payload_len(payload_len) = TRANSPORT_HEADER_LEN + payload_len`.
- `fits_esb_payload(esb_payload_len, payload_len)` returns true when both the
  ESB payload length cap (`EsbHeader::MAX_PAYLOAD = 252`, `src/header.rs`) and
  the framing cap (`MAX_TRANSPORT_PAYLOAD_LEN = 247`) are respected.
- `validate_payload_length(...)` is the `Result`-returning variant for board /
  transport configuration validation. It is intentionally separate from
  `EsbConfig::validate()` because the base ESB config cannot know which
  higher-level transport will wrap the payload.

`encode_frame` and `decode_frame` round-trip a complete frame. `decode_frame`
only consumes `TRANSPORT_HEADER_LEN + payload_len` bytes; trailing bytes after
the declared payload are ignored (covered by
`decode_frame_ignores_trailing_bytes_after_declared_payload`), so a transport
frame may sit inside a larger ESB payload buffer if a board needs that.

## Transport ACK Wire Format

The transport ACK is a fixed 4-byte blob carried inside an ESB ACK payload
(`src/transport.rs`):

```text
byte 0: TRANSPORT_ACK_MAGIC low byte  (0x54)
byte 1: TRANSPORT_ACK_MAGIC high byte (0x41)
byte 2: device_id
byte 3: sequence
```

`TRANSPORT_ACK_MAGIC = 0x4154` is the ASCII string `"TA"` and is written
little-endian on the wire, so the bytes appear as `0x54, 0x41`
(`encode_decode_transport_ack_round_trips_typical_and_boundary_values` pins
this). `TRANSPORT_ACK_LEN = 4`.

Encoding / decoding:

- `encode_transport_ack(ack, out)` writes the 4 bytes into `out[..4]` and
  leaves any trailing bytes in `out` untouched. It rejects buffers shorter than
  `TRANSPORT_ACK_LEN` (covered by `encode_transport_ack_rejects_undersized_output`
  and `encode_transport_ack_accepts_larger_buffer_without_touching_trailing_bytes`).
- `decode_transport_ack(buf)` requires the magic to match exactly and the buffer
  to be at least `TRANSPORT_ACK_LEN` bytes. It ignores trailing bytes, so it can
  be called on an ESB ACK payload that is longer than 4 bytes
  (`decode_transport_ack_ignores_trailing_bytes`). It rejects every short prefix
  (`decode_transport_ack_rejects_undersized_buffer`) and every perturbation of
  the magic (`decode_transport_ack_rejects_wrong_magic`).

`TransportAck::matches(device_id, sequence)` compares both fields; either
mismatching fails (covered by `transport_ack_matches_only_when_device_and_sequence_agree`,
including 0/255 boundaries in `transport_ack_matches_at_u8_boundaries`).

The ACK is delivered via the ESB ACK payload path, not as a separate frame. In
the MPSL PRX adapter the board-level provider
`PrxAckExtensionProvider = fn(u8, &[u8], bool) -> PrxAckExtension`
(`src/mpsl_timeslot.rs`) runs in the PRX RADIO callback after the raw payload is
queued, returns the 4-byte transport ACK bytes, and the adapter attaches them to
the ACK packet for the pipe the frame was received on. On the PTX side the ACK
bytes are surfaced back to the application via the send result's `ack_extension`
field (see the elytra example below).

## FLAG_ACK and FLAG_RETRANSMIT Semantics

- `FLAG_RETRANSMIT (0x02)` marks a frame as an application-level retransmit of
  an earlier sequence number. It is purely informational at the framing layer:
  `accept_bound_frame` does **not** interpret it. Dedup is driven entirely by
  `(device_id, sequence)` in `SequenceTracker`, so a retransmitted frame is
  accepted the first time it arrives and dropped as a duplicate on every repeat
  until the tracker entry for that device is reset
  (`accept_bound_frame_accepts_retransmitted_frame_as_new_after_reset`).

- `FLAG_ACK (0x01)` is reserved for frames that themselves carry an
  application-level acknowledgement in their payload. It is defined and
  round-trips through the header
  (`transport_header_accepts_both_flags_set_together`), but the current
  transport ACK path carries the ACK as an ESB ACK payload, **not** as a framed
  transport payload, so no in-tree board firmware sets `FLAG_ACK` today. It is
  kept in `FLAGS_V1_MASK` so a future "ACK-in-frame" variant can use it without
  a version bump.

## SequenceTracker (Duplicate Suppression)

`SequenceTracker<const N: usize>` (`src/transport.rs`) is a per-device
last-seen-sequence table. It exists because ESB's 2-bit PID only catches
radio-level repeats on a pipe; any application that retries above ESB needs
dedup keyed by `(device_id, sequence)`.

Layout: `valid: [bool; N]` plus `last: [u8; N]`, indexed by `device_id`.

- `accept(device_id, sequence)` returns
  - `Err(InvalidParam)` if `device_id >= N`,
  - `Ok(false)` if `valid[device_id]` is already true and `last[device_id]`
    equals `sequence` (a duplicate),
  - `Ok(true)` and records the sequence otherwise.
- `reset_device(device_id)` clears one device's slot. After a reset, the same
  sequence is accepted again as new. This is the hook the central side uses when
  it wants to accept a fresh stream from a peripheral (for example after a
  known reboot or re-pair). Without a reset, repeats are permanently dropped.

Per-device behaviour is independent: device 0 seeing sequence 1 does not affect
device 1 seeing sequence 1
(`sequence_tracker_accepts_new_and_rejects_duplicates_per_device`).

## StaticBindingTable (Pipe to Device Routing)

`StaticBindingTable<const N: usize>` (`src/transport.rs`) maps each local ESB
pipe to the single application-level `device_id` allowed to send frames on it.
It is intentionally small and generic; pairing, persistence, and policy belong
in higher-level firmware.

- `from_pipe_entries([Option<u8>; N])` supports const initialization.
- `bind(pipe, device_id)` / `unbind(pipe)` mutate one entry at a time.
- `device_for_pipe(pipe)` returns `Option<u8>`.
- `accepts(pipe, device_id)` returns true only when the pipe is bound and bound
  to exactly that `device_id`.
- All accessors return `Err(InvalidParam)` for out-of-range pipes.

`accept_bound_frame(bindings, tracker, pipe, frame)` ties the pieces together
into the common PRX receive flow (`src/transport.rs`):

1. `decode_frame(frame)` - rejects truncated frames, wrong versions, and flags
   outside `FLAGS_V1_MASK`.
2. `bindings.accepts(pipe, header.device_id)` - rejects frames whose
   `device_id` is not bound to the receiving `pipe`.
3. `tracker.accept(header.device_id, header.sequence)` - returns `Ok(None)` for
   duplicates, `Ok(Some((header, payload)))` for a new accepted frame.

Return values (as of `src/transport.rs`):

- `Ok(Some((header, payload)))` - new accepted frame, caller should apply it.
- `Ok(None)` - duplicate, caller should silently drop.
- `Err(InvalidParam)` - malformed frame, binding mismatch, or `device_id`
  outside the tracker.

## Usage Example: Elytra Split Firmware

The elytra board firmware uses this transport for its left/right split link.
`RIGHT_DEVICE_ID` is the right half; the left half is the central/PRX.

### PTX side (right half, `boards/elytra/src/main.rs`)

For every matrix snapshot, the right half encodes a transport frame with
`FLAG_RETRANSMIT` set on every attempt after the first, and re-sends until the
transport ACK matches:

```rust
let flags = if attempts == 0 { 0 } else { transport::FLAG_RETRANSMIT };
let frame_len =
    transport::encode_frame(RIGHT_DEVICE_ID, snapshot_seq, flags, &report, &mut frame)
        .unwrap();
// ...session.send(&frame[..frame_len]).await...
if result.ack_ok {
    if let Some(extension) = result.ack_extension {
        if let Ok(ack) = transport::decode_transport_ack(extension.as_slice()) {
            if ack.matches(RIGHT_DEVICE_ID, snapshot_seq) {
                break; // end-to-end delivery confirmed
            }
        }
    }
}
```

Note that `result.ack_ok` (the ESB hardware ACK) is necessary but not sufficient:
the loop only breaks once `ack.matches(...)` confirms the application-level
transport ACK for this exact sequence. This is the two-layer ACK split in
practice.

### PRX side (left half, `boards/elytra/src/bin/left_central.rs`)

The left half validates `pipe -> device_id` statically and acknowledges only
after the generic PRX event queue has accepted the frame:

```rust
let bindings = StaticBindingTable::<8>::from_pipe_entries([
    None,
    Some(RIGHT_DEVICE_ID),
    None, None, None, None, None, None,
]);
let mut tracker = SequenceTracker::<1>::new();

// In the PRX RADIO callback, produce the ACK extension:
fn right_transport_ack_extension(pipe: u8, payload: &[u8], queued: bool) -> PrxAckExtension {
    if !queued || pipe != 1 {
        return PrxAckExtension::EMPTY;
    }
    let Ok((header, _)) = decode_frame(payload) else {
        return PrxAckExtension::EMPTY;
    };
    if header.device_id != RIGHT_DEVICE_ID {
        return PrxAckExtension::EMPTY;
    }
    let mut bytes = [0u8; TRANSPORT_ACK_LEN];
    if encode_transport_ack(
        TransportAck::new(header.device_id, header.sequence),
        &mut bytes,
    )
    .is_err()
    {
        return PrxAckExtension::EMPTY;
    }
    PrxAckExtension::from_slice(&bytes).unwrap_or(PrxAckExtension::EMPTY)
}

// In the application task, consume validated frames:
let (header, payload) = match accept_bound_frame(
    &bindings, &mut tracker, ev.pipe, frame,
) {
    Ok(Some(frame)) => frame,
    Ok(None) => continue,          // duplicate
    Err(_) => { /* log and continue */ }
};
```

Two details worth calling out from this example:

- `right_transport_ack_extension` withholds the ACK when `queued` is false or
  the pipe/device is wrong, so a frame is only acknowledged once the central has
  actually accepted it for processing.
- The provider runs in the MPSL RADIO callback, so it only does bounded parsing
  and fixed-size copies. This matches the
  `PrxAckExtensionProvider: fn(u8, &[u8], bool) -> PrxAckExtension` contract in
  `src/mpsl_timeslot.rs`.

## Known Limitations and Future Work

- **Single-pipe backchannel.** The transport ACK rides inside an ESB ACK
  payload, so its bandwidth is bounded by the PRX->PTX ACK payload size and by
  the radio schedule. Under MPSL coexistence this backchannel is the
  scarce direction; see `docs/m10-verification.md` for measured ACK return rates
  under various PRX slot profiles.
- **No ACK-in-frame today.** `FLAG_ACK` is defined and round-trips, but the
  current transport ACK path is always carried as an ESB ACK payload, never as a
  framed transport payload. No in-tree board firmware sets `FLAG_ACK`.
- **`SequenceTracker` does not wrap.** The tracker stores a single last-seen
  `u8` sequence per device and treats equality as a duplicate. Sequence numbers
  are not interpreted as a monotonic counter; wrapping from 255 to 0 would be
  accepted as new. This is fine for the current peripheral pattern (one snapshot
  per send, retries reuse the same sequence) but a future design that advances
  sequence continuously must account for the 256-value space.
- **`reset_device` is the only re-synchronization hook.** A central that wants
  to accept a re-stream from a peripheral must call `reset_device` explicitly.
  There is no automatic reset-on-(re)pair or reset-on-session-start in the
  transport layer; that policy belongs to the higher-level firmware.
- **No transport-layer fragmentation.** A frame must fit in one ESB packet, i.e.
  `payload_len <= MAX_TRANSPORT_PAYLOAD_LEN (247)`. Larger application messages
  need their own chunking above this layer.
- **Pairing and persistence are out of scope.** `StaticBindingTable` is static;
  the transport does not define how bindings are populated or persisted.

## Test Coverage

As of commit `55faba2`, the transport module has 26 host tests
(`cargo test --lib --target x86_64-unknown-linux-gnu --features nrf52840`),
covering:

- Frame encode/decode round trips and trailing-byte tolerance.
- Rejection of truncated frames, wrong versions, and flags outside the v1 mask.
- Payload sizing helpers and the 247-byte framed payload cap.
- `TransportAck::matches` including 0/255 boundaries.
- Transport ACK encode/decode round trips, including boundary `(device_id,
  sequence)` pairs and the exact wire layout `0x54, 0x41, device, seq`.
- Transport ACK rejection of undersized buffers and wrong magic.
- `FLAG_ACK` / `FLAG_RETRANSMIT` disjointness, combination, and round trip
  through a full frame.
- `SequenceTracker` accept/duplicate/reset semantics per device.
- `StaticBindingTable` bind/unbind/accepts and const initialization.
- `accept_bound_frame` binding validation, duplicate dropping, and acceptance
  after `reset_device`.

The tests are the authoritative statement of protocol semantics; this document
is a companion to them, not a replacement.
